## 三、组合攻击链（跨端风险联动，按危害排序）

1. **链 A｜公网伪造签署（法律效力）**：CP 零鉴权（CP-1）+ 回调验签 fail-open（CP-2）+ HTTP 明文部署（47.116:8281）→ 任何能到达端口的人可发起真实 e签宝流程、伪造"签署完成"回调、为任意账号换取任意流程签署链接、撤销任意流程。**无需任何漏洞链组合，单点直达。**
2. **链 B｜跨租户盗号**：studio-web files-api 任意路径读（WEB-1）→ fleet 模式所有租户 worker 同机、每用户 `auth.json` 同盘 → 读取他人 accessToken/refreshToken → 冒充任意租户调用后端。
3. **链 C｜桌面端本机沦陷**：渲染层任意 XSS（恶意依赖/DOM 注入）→ host-api `shell.openExternal` 无协议白名单（FE-1）或 `shell:openPath` 任意路径执行（FE-2）→ 本机任意执行；`file:readText` 任意读（FE-3）+ `chat.send` 外传敏感文件。
4. **链 D｜供应链**：更新不验签（FE-4）+ 裸 IP 更新源 `https://47.116.163.57:8082`（SHA512 与安装包同服务器）→ 服务器被控即向全部 Windows 客户端推送任意代码。
5. **链 E｜计费旁路并存**：register 路径漏发 FREE 套餐默认 PRO/11000（BE-1）+ `/internal/tools/**` 不在权益门禁（BE-3）+ CP 侧零配额裁决 → 免费白嫖；同时 `chargeForSigning` 无并发锁（BE-2）+ CP 无幂等（CP-5）→ 重复扣费。**两个方向的损失同时存在。**

## 四、CRITICAL（10 项，上线阻断）

### CP-1｜control-plane 全部端点零鉴权（已亲手复核）
- `control-plane/src/main/java/com/jyfc/cp/controller/CpSigningController.java:34-40`（execute/sign-url/revoke/extend/download/rescind/antchain-* 共 7 端点）
- 证据：全模块 grep `Authorization|Security|Filter` 零命中；pom.xml 无 spring-boot-starter-security。DP 的 `CpSigningClient.java:193-195` 发送 `Authorization: Bearer`，CP 侧从不读取。`server.port: 8281` 绑全网卡。
- 影响：公网任何人可创建真实签署流程（法律效力+e签宝计费）、换任意 flowId 签署链接（`needLogin:false`）、撤销/解约任意流程、下载已签文件；CP 对请求零租户/零配额/零套餐裁决——D16 的 chokepoint 只剩"转发"。
- 建议：Spring Security 或 OncePerRequestFilter 强制校验 Bearer JWT（iss/aud/exp/签名）；按 claim 限定租户与配额；绑内网 + 反代 mTLS/IP 白名单；登录加限流。

### CP-2｜e签宝回调验签 fail-open（已复核模块级证据）
- `control-plane/src/main/java/com/jyfc/cp/controller/EsignCallbackController.java:60-67`
- 证据：`if (timestamp != null && signature != null)` 才验签——**头缺失直接放行**；`@RequestHeader(required = false)` 主动允许缺失；无时间戳新鲜度窗口（永久可重放）；不校验 App-Id 头。
- 影响：一条不带签名头的 `{"action":"SIGN_FLOW_UPDATE","flowId":"..."}` POST 即可把参与方置 SIGNED、任务自动 COMPLETE——凭单条 HTTP 请求伪造法律签署状态。另：验签失败返回 HTTP 200 + `code:403`，e签宝会停止重试，真实事件被永久丢弃。
- 建议：fail-closed（头缺失即 403，HTTP 状态码一致）；±5 分钟时间窗；比对 App-Id。

### CP-3｜`SIGN_FLOW_UPDATE` 一律映射为"已签署"
- `EsignCallbackController.java:96-100`：`yield "SIGNER_SIGNED"; // 简化：默认当作签署完成`
- 影响：该事件是 e签宝的伞形事件（含查看、转换等中间态）——**无需攻击者**，正常回调即可把没人签的合同标成已完成。
- 建议：按 `signResult`/`flowStatus` 子字段细分，仅"该签署人已签署"子事件才映射；其余入事件表。

### CP-4｜泄漏的 e签宝密钥仍在 target/ 旧 jar（需立即轮换）
- `control-plane/target/control-plane-1.0.0.jar → BOOT-INF/classes/application.yml`：`app-id: ${ESIGN_APP_ID:7439140178}`、`app-secret: ${ESIGN_APP_SECRET:15864da4212bff60f541f068d47dcf8a}`（源码 yml 09-25 已移除明文，但可部署的旧 fat jar 仍带兜底值）。
- 建议：立即在 e签宝控制台轮换 secret；`mvn clean` 删旧产物；所有密钥去兜底值、启动 fail-fast。

### CP-5｜送签无幂等 + DP/CP 超时错配 → 重复法律流程/重复扣费
- `EsignSigningService.java:38-44`（对 taskRef 无去重，CP 无持久化）vs `CpSigningClient.java:190`（`.timeout(Duration.ofSeconds(5))`）。
- CP 最坏链路（上传 60s + 轮询 5×1.5s + 建流程 30s）轻松超过 DP 的 5s → DP 抛"CP 不可达"，CP 继续成功创建真实流程；DP 幂等护栏（`providerFlowId != null`）只在成功响应后生效 → 用户重试即第二条流程。
- 建议：taskRef 幂等键落库（重复返回既有 flowId）；或 execute 异步化（202+查询）；至少把 DP 超时调到 ≥ CP 最坏耗时。

### BE-1｜docker-compose 编排启动后端必然崩溃（已复核）
- `docker-compose.yml:46-51`（无 SPRING_PROFILES_ACTIVE，已 grep 复核）+ `backend/.../core/config/ProductionConfigValidator.java:32-35`（无 profile 即抛）+ `application.yml:82`（`jy.cp.mode` 默认 required，compose 里却没有 control-plane 服务）。
- 影响：按编排/文档部署开箱即崩；即使加 profile，签署全链路 100% 失败。`deploy/README-部署教程.md:59` 生产变量清单同样漏 profile。
- 建议：compose/Dockerfile 加 `SPRING_PROFILES_ACTIVE: prod`；compose 增加 CP 服务或单机用 `CP_MODE: local`；deploy README 补齐。

### BE-2｜迁移合并使既有库不可原地升级（破坏性变更未声明）
- V130–V147 合并为单文件 `V130__legal.sql`，同时**已应用的 V001/V110 被就地改写**；`validate-on-migrate: true` + `ignore-missing-migrations: false` → 任何跑过旧迁移的库启动即 checksum mismatch / missing migration。
- 影响：任何已部署环境无法升级；操作方式是"先 dump 再删库"（工作区残留 `jy_financial_predrop_20260923_234601.sql` 为证）。
- 建议：在 V130 头部与发布说明显式声明"需删库重建 + 数据回放步骤"；今后用新增迁移而非改写历史。

### WEB-1｜files-api read 模式仍放行任意绝对路径 → 跨租户读 auth.json（已亲手复核，上次 CRITICAL 未修复）
- `studio-web/server/host-core/services/files-api.ts:389-412`：read 分支对任何路径 `return { realPath: real, readOnly: true }`。
- 三个入口/向量：① 本体（readText/readBinary/stat/listDir/listTree 全经此函数）；② legacy 通道 `server/host-core/main/ipc-handlers.ts:1438-1510` 经 `legacy-router.ts:73-79` 直达；③ `files-api.ts:443-479` `stagePaths` 对 filePath 零校验即 copyFile，把宿主机任意文件拷进自己目录再读。
- 攻击链：fleet 模式每租户 worker 同机，`server/src/fleet/layout.ts:107` 的 `<DATA_DIR>\users\<scope>\auth.json` 存有各租户后端 token → 任意已登录用户可窃取任意他人 token、读宿主机 .env/密钥。
- 建议：read 分支同样限定「本 worker 用户根 + 授权 workspace 根」（同文件 745-810 行 `statWorkspaceFile` 已有正确示范）；stagePaths 同款校验；两份重复实现必须同改或合一；web 端可从 legacy-router 名单移除 `file:*` 五通道。

### FE-1｜Windows 更新链不验签 + 裸 IP 更新源（上次 CRITICAL 未修复）
- `studio-frontend/electron-builder.yml:112-114`（`verifyUpdateCodeSignature: false` 原样存在）+ `electron/main/updater.ts:19`（`https://47.116.163.57:8082`，运行时 `setFeedURL` 无条件覆盖 yml publish 配置）。
- 影响：更新源服务器被控 = 全客户端任意代码推送。另 `electron-builder.obfuscated.yml` 与 updater.ts 的 publish 事实源互相矛盾。
- 建议：代码签名证书 + 删 `verifyUpdateCodeSignature:false`；更新源换域名+TLS 的 CDN；统一 publish 事实源。

### FE-2｜桌面 host-api 旁路旧 IPC 的 shell 防护 → 本机执行链
- `electron/services/shell-api.ts:30-32`：hostInvoke 通道的 `openExternal` **无协议白名单**（旧通道 `ipc-handlers.ts:1087-1089` 有 `https:/http:` 白名单——同一操作两条通道只有一条有防护）；`ipc-handlers.ts:1104-1106` `shell:openPath` 任意路径（Windows 上即执行）；`electron/gateway/clawhub.ts:112-118` uninstall 的 `slug` 未校验 → `..\..\` 逃逸后 `rm -rf` 递归强删任意目录。
- 建议：抽共享协议白名单供两通道复用；openPath 加扩展名白名单；slug 复用 SAFE_ATTACHMENT_ID 正则 + isInside 复核。
