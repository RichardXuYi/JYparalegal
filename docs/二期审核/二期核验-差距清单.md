# 二期核验：差距与偏离清单

核验日期：2026-09-27。核验对象：`docs/prd/01~08` + `docs/demo/mock-court-demo.html` 所述需求，对照当前代码实际状态。

方法：逐份读 PRD 与 demo，再逐文件核验后端（`backend/src/main/java/com/jyfc/backend/module/moot/`）、宿主驱动器（`studio-web/server/src/moot-driver.ts`）、前端（`studio-web/src/pages/MockCourt/`、`studio-frontend/`）。每条结论均给出 `文件:行号` 证据。本清单只依据当前代码，不引用任何历史记忆。

## 0. 总体结论

方向大体正确：档案与庭审正文确实全部落在本机文件夹 JSON，未往平台库 `jy_financial` 加表、未执行 `公司档案库/V1__archive_and_moot.sql`、未引入向量库、未污染 `knowledge_entries`、防目录穿越（`normalize()` + `startsWith(root)`）覆盖完整。五槽/六角色编排状态机（prepare 幂等、commit 拒重复、skip、close 清 sessionKey）、消息四块组装、庭审记录「首次全文/再次增量/会话丢失回退全文」均已在后端 `MootService` 落地且与 PRD 一致。

问题集中在三处：
1. **两处明确违反 PRD 禁令**（studio-frontend 未保持占位 + 接了第二套驱动器；上传未用 multipart）。
2. **一批功能缺口/语义偏离**（真人槽只在第 4 槽、解析失败被吞、检索查询句被截断、事件命名不符、前端 JSX 语法错误等）。
3. **前端与 demo 布局稿差距很大**（庭审/档案/案卷三视图的核心结构大量缺失）。

## A. 方向性偏离（违反 PRD 明确禁令，优先处理）

### A1. studio-frontend 桌面壳未保持占位，且接了第二套驱动器
- PRD 要求：`06-前端` 第 5 行——「桌面壳 studio-frontend 的同名占位页保持占位，不接第二套驱动器。庭审以 studio-web 为准」。
- 现状：
  - `studio-frontend/src/pages/MockCourt/index.tsx` 与 `studio-web/src/pages/MockCourt/index.tsx` **逐字节相同**（`diff` 结果 IDENTICAL），不是占位页。
  - `studio-frontend/electron/services/moot-desktop-step.ts` 存在，`desktopHearingStep()` 在 Electron 本进程内自跑 `prepare → chat.send → 轮询 history → commit`，并在 `studio-frontend/electron/main/ipc-handlers.ts:1154` 拦截 `/platform/moot/hearings/*/step` 走本地驱动。
  - 已挂载路由：`studio-frontend/src/App.tsx:43,337`（`/moot`），移动端入口 `studio-frontend/src/mobile/pages/More.tsx:97`。
- 影响：等于把庭审驱动器复制成两套（web + desktop），违反「以 studio-web 为准、桌面壳只占位」。
- 建议：把 studio-frontend 的 MockCourt 还原为「即将开发」占位页，移除 `moot-desktop-step.ts` 与 `ipc-handlers.ts` 中的 `/step` 本地拦截，解除 `/moot` 路由挂载或指向占位。

### A2. 上传接口用 base64 JSON，不是 multipart
- PRD 要求：`02-档案与检索` 上传节——`POST /api/moot/cases/{id}/files`，multipart；`07` 步骤 A 也以 multipart 为验收口径。
- 现状：
  - `MootController.java:46-49` 用 `@RequestBody Map<String,String>` 读 `fileName` / `contentBase64`，不是 `MultipartFile`。
  - `MootService.upload()` `MootService.java:95,100` 用 `Base64.getDecoder().decode`；解码后 `MAX_BYTES=50MB` 校验在 `MootService.java:101`（对**解码后字节**校验，本身正确）。
- 需要澄清的连带问题（修正之前口述中的不精确处）：`application.yml:8-12` 的 `max-file-size/max-request-size: 50MB` 属于 `spring.servlet.multipart` 段，**只作用于 multipart 请求，管不到这个 JSON 接口**。所以真实风险不是「被 50MB 请求体上限拦截」，而是：base64 字符串（约为原文件 1.33 倍）在浏览器和 JVM 堆里全量驻留、无流式处理，大文件有内存/健壮性隐患；同时那两条 multipart 限额对本接口形同虚设，属配置与实现不一致。
- 建议：改回 `MultipartFile` multipart 上传，`application.yml` 的 multipart 限额才真正生效；前端去掉 base64 编码。

## B. 后端（数据平面）功能缺口与语义偏离

### B1. 解析失败被静默吞成空串，缺 FAILED / PENDING 状态
- PRD 要求：`02` 解析节——解析失败标 `FAILED`，保留文件，错误信息落在该行；预览列表状态可见 `PENDING/PARSED/NO_TEXT/FAILED`。
- 现状：
  - `ArchiveText.extract()` `ArchiveText.java:25-27` 对任何异常 `return ""`，不留错误信息。
  - `MootService.java:114` 只按「抽出字是否为空」判 `PARSED`/`NO_TEXT`，**永远不会出现 FAILED**，也无 PENDING（同步解析）。
  - 后果：真正损坏/解析异常的文件被误标为 `NO_TEXT`，用户无法区分「扫描件无文字层」与「解析报错」。
- 注：`03`/`08` 数据模型只列 `PARSED/NO_TEXT`，与 `02`/`07` 的 `FAILED` 存在 PRD 内部张力；但「解析异常吞掉、不落错误信息」是明确缺陷。
- 建议：`ArchiveText` 区分「无文字层」与「抛异常」，异常路径落 `FAILED` + `parseError` 字段。

### B2. 支持格式解析缺口：doc/wps/xls/xlsx/rtf 一律 NO_TEXT
- PRD 要求：`02` 允许扩展名含 doc、wps、xls、xlsx、rtf；`07` 步骤 A 以「有文字层的 docx 或 pdf」为验收，其余可接受 NO_TEXT。
- 现状：`ArchiveText.java:19-24` 只解析 `docx/pdf/txt/md/csv`；`doc/wps/xls/xlsx/rtf` 走 `default -> ""`，即**这些格式即便有文字层也无法被检索**。
- 另：`MootService.java:29-30` 的 `ALLOWED` 比 PRD 多放行 `txt/md/csv`（放宽，属超集，方向偏离但风险低）。
- 影响：xls/xlsx（如 demo 里的「E-07 损失计算表.xlsx」）这类常见证据无法进入检索。
- 建议：至少补 xls/xlsx（POI 已引入）、rtf；或明确把这些标为 NO_TEXT 并在 UI 提示。

### B3. 切段为定长字符硬切，非「按段落累加」，且无页码/段落定位
- PRD 要求：`02` 切段节——按段落累加约 500–800 字、相邻段重叠约 100 字、带序号；能从解析结果拿到页码/段落号才填定位，不编造。
- 现状：`MootService.chunks()` `MootService.java:591-604` 固定 `size=700`、`overlap=100` 的**纯字符窗口硬切**，不识别段落边界，不产出任何页码/段落定位字段（`03` 数据模型 chunks 为字符串数组，序号靠下标隐式表达）。
- 影响：700/100 字数在 PRD 区间内，但会把「第 8 条」这类条款从中间切断，正是 PRD 想避免的「条号拆碎配错」。
- 建议：改为按段落累加到 500–800 字，尽量不在句/条中间断开。

### B4. 检索查询句被截断，「加发言末段」实际几乎不生效
- PRD 要求：`02` 谁来查/怎么查——查询句由服务端拼「本槽计划说明 + 一句发言末尾的一段」；条号/金额/日期按整段匹配。
- 现状（真实缺陷，需注意）：
  - `MootService.java:251` 拼 `plan_text + " " + tail(lastUtterance)`；`tail()` `MootService.java:613-616` 取末尾 80 字。
  - 但 `needle()` `MootService.java:606-611` 在没匹配到「第X条」时，**取整个查询句的前 40 字**。`plan_text` 通常已超 40 字，于是 `tail` 拼进来的发言末段被整段丢弃。
  - 结果：PRD 要求的「用发言末段辅助检索」在常见路径下不起作用；且金额/日期未按整段专门处理，只有「第X条」有正则。
- 建议：`needle` 应对 plan 与 tail 分别取词，或提高截断长度并支持金额/日期整段匹配。

### B5. 检索用内存 String.contains，非「参数化 LIKE / 同 KnowledgeService 风格」
- PRD 要求：`02` 怎么查第 2 点——参数化 `LIKE`，与 `KnowledgeService.searchKnowledge` 同风格。
- 现状：`MootService.hits()` `MootService.java:362-381` 对 chunk 做 `parts.get(i).contains(needle)` 内存子串匹配。因数据落 JSON 无 DB，属可理解适配，但与 PRD 明列风格不符（记录为偏离，非硬缺陷）。最多 5 段（`MootService.java:369`）、每段截 800 字（`:376`）符合 PRD。

### B6. 真人槽硬编码为 seq==4，未覆盖「我方为原告时第 1 槽真人」
- PRD 要求：`04` 五槽表——第 1 槽（原告）在「我方是原告且选择自己说」时为真人；`04` 真人节——我方槽可自选。
- 现状：
  - `openHearing` `MootService.java:182`：`human_roles = humanRoles.contains("OURS") ? "4" : ""`（把「我方自己说」硬编码成槽序号 4）。
  - `prepare` `MootService.java:239`：`human = "4".equals(human_roles) && seq==4`。
  - 后果：**只有第 4 槽能是真人**。当我方为原告（槽 1 是我方）并选择自己说时，槽 1 不会 awaitHuman。且 `human_roles` 用 seq 编码而非 role_code，语义偏离 `03` 数据模型。
- 建议：`human_roles` 记 role_code，按「该槽 role_code == OURS 且用户选自己说」判真人，覆盖槽 1 与槽 4 两种立场。

### B7. 「插话」机制缺失（commit 后追加 HUMAN 已完成槽）
- PRD 要求：`04` 真人节——插话在当前槽 commit 之后追加一条 `speaker=HUMAN` 的已完成槽，不并行调用 agent，原定下一位不变。
- 现状：`commit` `MootService.java:275` 强制槽为 `SPEAKING`，DONE 后无法再追加 HUMAN 插话；无独立插话入口。
- 建议：新增「向已 DONE 序列追加 HUMAN 发言」的接口/分支。

### B8. 开庭增加了 PRD 未要求的前置门槛
- PRD 未规定「必须有 PARSED 文件才能开庭」。
- 现状：`openHearing` `MootService.java:176` 无 PARSED 文件即抛「没有可检索的文字，不能开庭」。全为 NO_TEXT（仅图片/扫描件）的案卷无法开庭。
- 影响：额外收紧，可能挡住合法场景。建议确认是否为有意约束；若非，放开或改为警告。

### B9. 预览接口路径与 PRD 不一致
- PRD：`GET /api/moot/cases/{id}/files/{fileId}/content`。
- 现状：`MootController.java:56-60` 为 `GET /api/moot/cases/{id}/files/{fileId}?raw=`，缺 `/content` 段，用 `raw` 查询参数决定是否回原件 base64。
- 影响：接口契约与 PRD 不符（前端已按现状对接，属自洽偏离）。

### B10. 遗留：ArchiveProperties 含无用 DB 字段
- `ArchiveProperties` 仍带 `url/username/password` 等 DB 连接字段，在纯文件夹方案下已无意义，与「不连公司 MySQL」方向不 cleanly 一致（不影响功能）。建议清理。

## C. 宿主驱动器（studio-web/server）缺口与偏离

### C1. 事件命名与广播模型不符，多标签「只订阅」无法实现
- PRD 要求：`04`/`06`——事件 `slot-started / delta / slot-committed / await-human / hearing-closed`；「后打开的页面只订阅事件，不另起生成」。
- 现状：
  - `moot-driver.ts:155-217` 的 SSE 只发 `delta / human / done / error`，**五个 PRD 事件名一个都没有**（仅 `delta` 对得上）。
  - 事件仅在当次 `/step` 请求的 SSE 流内，未经 WS 广播转发；第二个标签直接吃 409（`moot-driver.ts:145-148`），**不是「只订阅」而是被拒绝**。
- 影响：违反事件契约；无法实现「第二窗口只看进度」。
- 建议：统一改为 PRD 五事件命名，并通过宿主 WS 广播，让非驱动窗口可只读订阅。

### C2. sessionKey 懒登记，未在开庭时为六角色统一开新 key
- PRD 要求：`05` 会话节——开庭时宿主为六个角色各开一个新 sessionKey，`PUT /hearings/{id}/sessions` 登记。
- 现状：`moot-driver.ts:175-188` 仅当某槽 `prepare` 未返回 sessionKey 时，才在 step 内构造 `agent:${agent_id}:h${id}` 并 PUT 整个 map（懒登记）。开庭（前端 `POST hearings`）是纯后端调用，宿主不在开庭时统一建/登记六把 key。
- 影响：与「开庭即登记六 key」时序不符；未点到的角色 key 可能一直为空。

### C3. 结案删除失败被吞，未上报、无「下场再删旧 key」
- PRD 要求：`05`——删不掉的 key 要在结案结果里报出来，下一场仍用新 key 并再删旧 key。
- 现状：`moot-driver.ts:244` `sessions.delete(...).catch(() => undefined)` 静默吞掉失败；结案结果不回报删除失败的 key；无「下场补删」逻辑。

### C4. 记忆快照仅进程级一次，且非严格「每场开庭前空快照」
- PRD 要求：`05`——开庭前为六角色记忆文件做空快照，结案时若不同则恢复。
- 现状：`moot-driver.ts:125,136-137` `snapshotMemories()` 只在首场 `ensureRoles`（受 `rolesReady` 守卫）执行一次，后续 hearing 不再快照；且是复制现有文件而非「空快照」。恢复在 `:247` cleanup 调 `restoreMemories()`。
- 影响：同进程内开第二场时，快照基准可能已是上一场残留，恢复语义与 PRD 有出入。

### C5. delta 为全量文本轮询，非 token 级增量（记录项）
- `moot-driver.ts:201-209` 每次 `send('delta',{text:latest})` 发的是轮询 `latestAssistant` 得到的整段最新文本，靠「连续 2 次稳定」判完成，非真正增量流。功能可用，但与「delta」语义有差距，且轮询 1.2s 有延迟。

### C6. 消息四块组装位置说明（非缺陷）
- 宿主直接转发后端 `prepare` 返回的 `turn.message`（`moot-driver.ts:192`），四块组装与「首次全文/再次增量/会话丢失回退」逻辑在后端 `MootService.message()` `MootService.java:332-360` 完成，且与 PRD 一致。此项**符合分工，不算缺口**，此处仅澄清之前「宿主未组装四块」的表述——组装本应在数据平面，已实现。

## D. 前端 /moot：缺陷 + 与 demo 布局稿的差别

### D1. 会导致构建失败的 JSX 语法错误（需立即修）
- `studio-web/src/pages/MockCourt/index.tsx:229-233`：stance 的 `<select>` 缺少开始标签 `<label>立场`，第 233 行是孤立的 `</label>`（第 228 行已闭合上一个 label）。这是不配对的闭合标签，JSX/TS 编译会报错。
- 现状证据：第 223-228 行是「已签合同」label+select 正常配对；第 229-232 行的 stance select 无 label 包裹、无标签文字；第 233 行多出 `</label>`。
- 建议：补回 `<label className="text-meta text-muted-foreground">立场`，删除或配对第 233 行。

### D2. 与 demo 布局稿的结构性差别（功能可用，但视觉/信息架构差距大）
庭审视图（`index.tsx:274-320`）缺 demo 的核心结构：
- 无 `role-row` 三栏（原告·我方 side-card / 合议庭 bench-card 含审判长·陪审员·书记员 role-chip / 被告·对方 side-card）。
- 无 `floor-bar`（🎤发言权锁定 / 🔇静音名单 / 约束 badge）。
- 无当前发言角色高亮（floor）。
- 无双 slots-bar 的 done/now/human chip 状态、无 ▶自动播放。
- 笔录块 `utt-head` 缺 HUMAN/AGENT tag + 阶段 plan + 时间。
- 右侧栏是「最近一槽档案片段」（`retrievals.slice(-5)`），非 demo 的「案情摘要 panel（案情/立场/本槽档案片段 chunkList/字数）」。

档案视图（`index.tsx:242-271`）：
- 缺 demo 左侧目录树（全部/合同/证据/说明与诉请/公司画像/证人名单 + 计数）。

其他：

- 开庭控件（「第 4 槽我自己说」checkbox + 开庭按钮）放在**档案视图**（`index.tsx:250-254`），demo 放在庭审 slots-bar。
- 固定声明「模拟发言，不是裁判文书」置于页顶全局 banner（`index.tsx:194-196`），demo 语境是放在笔录 panel 底部。

### D3. 已符合 PRD 的前端硬约束（记录，无需改）
- 用 `LegalPageHeader`（`index.tsx:2,193`）；三视图切换；案卷新建可选/不选 sign_task、填 stance+summary；档案一文件一行、点击开原件；庭审发言一条一块非聊天气泡；输入框仅 `humanSlot != null`（awaitHuman）时出现；条号「未在本槽片段中出现」警告（`index.tsx:27-32,294`）；不调 `chat.sendWithMedia`；不自行决定下一槽（调 `/step` 由后端返回）；不在浏览器持久化合同正文（无 localStorage/sessionStorage，预览走 `URL.createObjectURL`）；未做七维/隐藏推演/北大法宝/判决书导出。

## E. 建议修复优先级

| 级别 | 项 | 理由 |
