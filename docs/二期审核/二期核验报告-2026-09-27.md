### P0-3 检索实现与原方向偏离，实际会「永远检索不到」

PRD 02《谁来查 / 怎么查》规定得很硬：

> 查询句由服务端拼：本槽的计划说明，加上一句发言末尾的一段
> 参数化 `LIKE`，与现有 `KnowledgeService.searchKnowledge` 同一风格
> 条号、金额、日期按整段去匹配

实现（`MootService.needle()` + `hits()`，第 362–381、606–611 行）：

```java
private static String needle(String query) {
    var matcher = Pattern.compile("第\\s*\\d+\\s*条").matcher(query);
    if (matcher.find()) return matcher.group().replace(" ", "");
    String trimmed = query.trim();
    return trimmed.length() > 40 ? trimmed.substring(0, 40) : trimmed;   // ← 取前 40 字
}
...
if (!parts.get(i).contains(needle)) continue;   // ← 整段 contains 这一个串
```

而查询句是 `slot.plan_text + " " + tail(上一句)`，例如 `"被告答辩 我方已交付全部设备并经验收合格…"`。取前 40 字后拿去做 `contains`，**这段字面串在原文里出现的概率接近零**。结果就是 `hits()` 恒空 → 消息里恒写「本槽档案未检索到」→ 六个角色全部只能说「档案未检索到」。

这与 PRD 的核心意图（「让当前发言槽看到相关原文」「漏检可以接受，配错条款不能接受」）方向相反：现在是**没有漏检，是全检不到**。而且「条号、金额、日期按整段去匹配」这半句完全没有实现——`needle()` 只认 `第N条` 一种模式，金额和日期都没参与。

正确做法应是：把计划说明/末句切成若干关键词（条号、金额、日期优先），逐词对 chunk 做参数化 `LIKE`/`contains` 匹配，命中即返回该段，至多 5 段。

### P0-4 驱动架构与 PRD 明确规定的架构相反

PRD 04《驱动循环》与《中断》：

> 点名的是 studio-web 宿主里的驱动器。队列和笔录在公司数据平面。浏览器只订阅，不直接 `sendWithMedia`，避免两个标签各打一次模型。
> 同一 hearing 只有一个驱动。后打开的页面只订阅事件：`slot-started`、`delta`、`slot-committed`、`await-human`、`hearing-closed`。

实现是**每按一次「下一发言槽」→ 前端 `POST /platform/moot/hearings/:id/step` → 宿主只推一槽 → 断开**（`moot-driver.ts` 141–231，`MockCourt/index.tsx` 121–168）。差异：

- 宿主里**没有循环驱动器**，只有「一槽」这个无状态端点；推进节奏由浏览器按钮决定。
- **没有事件总线**。PRD 列的五个事件里，实现的 SSE 事件名是 `delta` / `human` / `done` / `error`，**没有** `slot-started`、`slot-committed`、`hearing-closed`。
- 「后打开的页面只订阅」做不到：页面拿不到进行中的事件流。第二个窗口只能自己再推一槽。
- 防并发只有 `const hearingLocks = new Set<string>()`（第 92 行），**是宿主进程内内存**，多用户/多进程/重启都不管用，也不是 PRD 要的「同一 hearing 只有一个驱动」。

这属于 PRD 点名的架构约束（「不建群聊」「一次只叫一个」「浏览器只订阅，不直接 sendWithMedia」）里**被明确写反的一条**。现在是浏览器在决定下一槽（PRD 06《页面不做什么》明写「不决定下一槽」）。

### 3.4 真人槽位置与 PRD 冲突

- PRD 04 第 1 行表格：槽 1 = 原告，「我方是原告且选择自己说时，**这一槽是真人**」；PRD 04《真人》也是「我方槽可以选择自己说」。
- 实现：`human_roles` 只在 `humanRoles.contains("OURS")` 时写 `"4"`，`prepare` 里 `num(slot.get("seq")) == 4` 才 `awaitHuman`（`MootService` 182、239 行）。
- 前端勾选框文案也写死「第 4 槽我自己说」（`MockCourt` 252 行）。

**结论**：真人只能占槽 4，槽 1（原告陈述）**永远不是真人**。而我方为原告时槽 4 的角色码就是 `OURS`（`roleOrder[3]`），所以「真人占 4」在**我方为原告时功能上凑巧等价于 PRD 的「我方槽是真人」**；但**我方为被告时**槽 4 仍是 `OURS`（被告），PRD 的槽 1 原告（OPPONENT）才是可选的真人槽——这里就错了。更根本的是 PRD 说的是「真人追加一条已完成槽」，实现是「真人占用原槽」，两者在「原定的下一位仍是下一位」这条上语义不同。

关于「**智能法庭是否与 demo 的框架有差别**」的正面回答：

**框架层面差别很大，不是细节差别。** demo 的庭审页信息架构是四层：
1. 视图流程条（案卷→档案→庭审，带完成态）
2. 槽位条（五个槽，done/now/human 三态）
3. **发言权锁条**（谁持有发言权、其余全员静音的显式可视化）——这是 demo 对 PRD「一次只叫一个角色」的核心可视化表达
4. 角色矩阵（我方 / 合议庭三人 / 对方）+ 主区（笔录流 + 输入区）+ 右侧（案情摘要 / 立场 / 本槽档案片段 / 字数）

当前实现在结构上只保留了「槽位条 + 笔录流 + 右栏（最近一槽片段）」，**第 3、4 层整体没有**。所以 demo 想表达的「单发言权锁 + 点对点调用 + 无群聊」这个约束，在页面上**看不出来**——而这恰好是本期最想讲给用户听的一件事。这一条不能算「样式差异」，属于 PRD 06「庭审页固定一句 / 上方五个槽和当前角色」的**可视化未落地**。

另有：**demo 的样例数据里带 `FAILED` 状态的「损坏文件.pdf」，实现没有 `FAILED` 这个态**（见 §3.1 #3），前端表格也没有对应渲染分支。

## 4. 收尾与清理项（P2）

1. `ArchiveUnavailableException` 已定义、已在 `GlobalExceptionHandler` 注册 503 映射，但**全仓库没有任何地方抛它**——死代码。要么在档案目录不可写时抛，要么删。
