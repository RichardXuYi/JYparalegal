# 竞品客户端架构对照分析（openclaw 系）— 2026-09-25

> **目的**：我们的桌面端内嵌 openclaw 网关，在 Windows 上因「遗留 workspace-state 迁移 fsync → EPERM → 网关 exit 78 → 无限重连」不可用。本机装有三家同类客户端（均为 openclaw 创始人公开批评过的魔改/同源产品）。本文拆解它们的架构与对 openclaw 的改造，提炼可直接借鉴的作业。
> **主研究对象：WorkBuddy**（唯一与我们同运行时——内嵌 openclaw fork——且活下来的）。Qoder CN / QwenWork 为对照（不嵌 openclaw 的另一条路线）。
> **方法**：只读检查安装目录与用户 home、对打包产物做指纹 grep、对照我们捆绑的上游 openclaw 2026.9.6、官方文档与 npm 版本核查。未修改任何第三方文件。

---

## 一、三家总览

| | WorkBuddy | Qoder CN | QwenWork（Qoder 同族） |
|---|---|---|---|
| 安装位置 | `D:\Program Files\WorkBuddy` | `D:\Program Files\Qoder CN` | `D:\Program Files\QwenWork\QwenWorkCN\<ver>` |
| 用户 home | `~/.workbuddy` | `~/.qwenworkcn` | `~/.qwenworkcn`（共用） |
| agent 运行时 | **fork 改名 openclaw**：`@genie/agent-cli`（`resources/app.asar.unpacked/cli/`） | **无 openclaw**：原生 `dws-core` + shim | **无 openclaw**：原生 `dws-core`/`qoderclicn` + shim |
| 状态/迁移 | 自有 home + 自有 sqlite 迁移命名空间 | 每会话工作区，无长驻全局状态 | **随包版本化 SQL 迁移** `resources/migrations/*.sql` |
| 运行时依赖 | 捆绑 `vendor/{node,python,PortableGit}.zip` → `binaries/` | 原生二进制 + 本地 MCP adaptor sidecar | 原生二进制 + sidecar |
| 更新 | 单目录 | electron-updater（`app-update.yml`） | **并列版本 + 原子切换 + 回滚**（`Launcher/Updater.exe` + `updater.cfg`） |
| 可诊断/修复 | `RepairApp.exe` + `startup-report.html` | — | helper 小 exe 隔离（`qwenworkhelper`/`vm-elevator`/`host-recycle-helper`） |
| 是否踩 Windows 迁移 EPERM | **否（打了补丁）** | 否（无该运行时） | 否（无该运行时） |

**关键结论**：三家都不踩我们踩的雷，但路径不同——WorkBuddy 是「嵌 openclaw 但把雷拆了」，Qoder/QwenWork 是「根本不嵌有状态 JS 运行时」。**我们是唯一"内嵌未打补丁 upstream + 认领共享遗留 state"的组合**，这正是踩雷的充分条件。

## 二、WorkBuddy 深潜（主参考）

### 2.1 身份确认：openclaw fork 换壳
- `resources/app.asar.unpacked/cli/package.json` → `name: @genie/agent-cli`，依赖含 `@agentclientprotocol/sdk`、`@genie/agent-*`、`@openai/agents`、`@tencent/agentdr-sdk`（在 fork 内核之上叠 ACP/厂商层）。
- `cli/product.{json,cloudhosted,selfhosted,ioa,internal}.json`：多部署形态靠 **flavor 配置**切换（`productConfigPathEnv: ACC_PRODUCT_CONFIG_PATH`），不分叉代码。
- `cli/vendor/{ripgrep,sandbox,shim,...}`：工具随包 vendored。

### 2.2 对 openclaw 的三处关键改造（= 我们的雷的拆法）
对照我们捆绑的上游 **openclaw 2026.9.6**（npm `latest` 与 `beta` 均为 2026.9.6，**无含修复的更新版本**）：

| # | 上游 2026.9.6 | WorkBuddy fork | 指纹证据 |
|---|---|---|---|
| 1 | `dist/worker/sqlite-store.worker.mjs` 存在**直接抛异常的目录 fsync** 调用点（`syncDirectorySync(...)`，5 处；best-effort 包装函数存在但迁移路径未用） | 同名目录同步函数**整段包 `try{}catch{}` 吞错**（Windows EPERM 被忽略，迁移继续） | fork：`…irectorySync(e){let el;try{el=openSync(e,"r"),fsyncSync(el)}catch{}finally{closeSync(el)}}` |
| 2 | 存在启动硬门禁：迁移不干净 → `refusing to report the gateway ready` / exit 78 | **硬门禁被移除** | fork bundle 中 `"did not complete cleanly"` 与 `"workspace-state"` **0 命中**；上游 `state-migrations.doctor-*.mjs` 中 `workspace-state` 7 命中 |
| 3 | 默认/认领共享 `~/.openclaw`（遗留全局状态） | **应用自有 home**，无 `.openclaw` 默认 | fork bundle `".openclaw"` 0 命中；home 为 `~/.workbuddy` |

> 我们的实测互证：把网关指向**全新空 state dir** 时，上游 2026.9.6 无需任何补丁即 `ready`（~10s）；指向含遗留状态的目录（`~/.openclaw`、`~/.grandpoem-studio/openclaw-dev`）即 EPERM/exit 78。说明雷 = 「遗留状态 × Windows fsync × 硬门禁」三者叠加；fork 拆了 1+2+3 中的任意一个都能活，我们拆了 3。

### 2.3 其它可抄工程实践
- **捆绑运行时**：`resources/vendor/{node,python,PortableGit}.zip` 首跑解压到 `~/.workbuddy/binaries/` → 不依赖系统 node。（我们网关日志有 `current Node failed runtime admission → 回退系统 node`，正缺这个。）
- **修复/诊断产物**：随包 `RepairApp.exe`（.NET 4.6.2）+ `startup-report.html`、`conversation-report.html` → 把"起不来"变成用户/客服可读报告 + 一键修复入口。
- **自有迁移命名空间**：`~/.workbuddy/.workbuddy-sqlite-migrations/`（应用自己的迁移账本，与 openclaw 内部迁移分离）。

### 2.4 映射到我们的行动项
| 行动 | 状态 | 说明 |
|---|---|---|
| 自有全新 state dir（拆雷 #3） | ✅ 已实施并验证 | `user-scope.ts` 默认 `~/.grandpoem-studio/openclaw/{primary,u<id>}`；dev override 更名 `openclaw-dev-96`；回退开关 `JY_CLAIM_LEGACY_OPENCLAW=1`。网关 ready/running 实测通过 |
| fsync 钉版本补丁（拆雷 #1） | ⬜ 预案 | 仅当需要**老用户升级连续性**（指回旧目录）时做：postinstall/pnpm patch，钉 openclaw 版本+哈希，把 `sqlite-store.worker.mjs` 的目录 fsync 包 win32 try/catch；失配即报警。仓库已有 postinstall 补丁先例 |
| 删迁移硬门禁（拆雷 #2） | ⛔ 不建议 | 改变失败语义（真故障也不再拒启），比 #1 侵入大；仅在 #1 不足时考虑 |

## 三、Qoder CN（对照：不嵌 openclaw 的路线）

- `app.asar`（5272 项）**0** openclaw/gateway/state-migrations 命中；`app.asar.unpacked/node_modules` 无 openclaw；全目录 `find -iname "*openclaw*"` 0 文件。
- CLI：`~/.qwenworkcn/bin/dws(.cmd)` → shim → **原生** `ext/cli-common-shim-windows-amd64.exe` → `dws-core-<platform>`；shim 内 openclaw 字符串 0 命中。
- 能力经**本地 MCP adaptor sidecar**：`~/.qwenworkcn/mcp-adaptor.config` → `127.0.0.1:54365` + token（独立进程，可单独重启/升级）。
- 插件/资源：**sha256 钉死的 manifest 包**（`bundled-resources/manifest.json`：sha256、`maxEntries`/`maxExpandedBytes` 防 zip-bomb/slip、`presence: ensure-minimum`、按文件夹解压）。
- 状态：**每会话** `workspace/<id>/` + `file-history/` + `shell-snapshots/` + `.models/` 缓存 → 无跨版本长驻全局状态 → 天然无"遗留迁移"类 bug。
- 更新/提权：`app-update.yml`（electron-updater）+ `elevate.exe`。

**启发**：把 agent 运行时放到**协议边界之外**（sidecar/原生进程），客户端升级就永远不被运行时状态迁移绑架；资源分发用哈希钉死 + 体积上限。

## 四、QwenWork（对照：同族 + 两条额外可抄模式）

与 Qoder CN 同族证据：`resources/bin/` 同时含 `dws-core-windows-amd64.exe` 与 `qoderclicn.exe`/`qoderclicn-legacy.exe`；`resources/qoder-auth-wasm/`（共享 WASM 认证）。

- **并列版本安装 + 原子更新/回滚**：`Launcher.exe` + `Updater.exe` + `updater.cfg`（`currentVersion`、`lastUsedTimestamps`、`pendingActivation`、`pendingCleanup`、`installingVersions`、`buildChannel`）；三个版本目录（1.0.5/1.0.6/1.2.0）共存 → 升级=装新版→原子切换→失败回退→事后 GC。**防"新版本把网关搞砖"的保险**（我们覆盖式安装无回退）。
- **应用自有、随包版本化 SQL 迁移**：`resources/migrations/0000…0011_*.sql`（命名露 lineage：`anthropic_multi_account`、`remove_claude_code_credentials`）→ 迁移在应用自己的命名空间、随版本走，不依赖第三方运行时启动门禁。
- **助手进程隔离**：`qwenworkhelper.exe`（提权）、`vm-elevator.exe`（VM/沙箱提权）、`host-recycle-helper.exe`、`open-with-helper.exe` → 易崩/需提权操作不进主进程。
- 浏览器集成：`native-messaging-host/` + `chrome-extension/`；人格模板：`awareness-templates/`（IDENTITY/SOUL/USER/MEMORY）。
- `app.asar`（34083 项）0 openclaw → 同 Qoder CN，不嵌 openclaw。

- **P0（已完成）**：自有全新 state dir（A）；重连遮罩不再无限锁屏；TopBar 去硬编码身份；侧栏区块沉底。

## 七、证据附录

- 时间线（2026-09-25 实测）：遗留 dir → 网关 spawn 后 ~19.5s `EPERM: operation not permitted, fsync` → `refusing to report the gateway ready` → exit 78 → ~21s/轮重连；全新空 dir → `http server listening`(7.0s) → `[gateway] ready`(~10s)；桌面首启 launch→running ≈54s。
- 上游指纹：`dist/worker/sqlite-store.worker.mjs` 5 处抛异常 `syncDirectorySync(`；`dist/state-migrations.doctor-Bb26RMA2.mjs` `workspace-state` 7 命中；`npm view openclaw` → installed=latest=beta=2026.9.6。
- fork 指纹：WorkBuddy `cli/dist/codebuddy.js` 目录同步 `try{openSync(e,"r"),fsyncSync(e)}catch{}`；`did not complete cleanly`=0、`workspace-state`=0、`".openclaw"`=0。
- 官方文档：`openclaw update repair` / `doctor --fix` / `triage`；env `OPENCLAW_STATE_DIR`、`OPENCLAW_CONFIG_PATH`、`OPENCLAW_SERVICE_REPAIR_POLICY`；文档承认 Windows 缺父目录同步保证；**无**跳过迁移的 env 开关。
- 社区：Windows fsync-on-read-only-fd → EPERM 的 `"r"→"r+"` workaround（媒体路径，与我们迁移路径不同点，不可直接套用）。
- 决策记录：用户明确「不想用旧的，仅从新的开始」→ 不对旧状态跑 `doctor --fix`/`update repair`；`~/.openclaw`、`openclaw-dev` 原样保留但桌面不再使用。
