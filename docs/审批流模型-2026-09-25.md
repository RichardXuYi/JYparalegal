# 审批流模型设计备忘（2026-09-25）

> 对应审计论断 H11 / deepseek #16。**本备忘只出方案，不改代码**：在审批模型定案前，
> 给 `approval_flow_id` 加任何"SUBMIT 前必须已审批"的硬门禁都会阻断全部签署，
> 因为当前系统里不存在任何能产生"已审批"状态的地方。

结论：该字段是指向**外部审批系统**的裸引用（一个 Long），既无状态契约也无回写通道，
"只写不读"意味着它在法律与计费链路上不构成任何控制。

## 二、候选模型

**A. 自建审批实体（控制力最强，工作量最大）**
新增 `approval_request`（task_id、发起人、当前节点、状态 PENDING/APPROVED/REJECTED、
审批人、时间戳）+ 节点配置（单人/会签/顺签）。签署任务 SUBMIT 前校验存在 APPROVED 记录。
需要：管理端审批界面或至少 API、通知、与租户组织架构（owner/admin/成员）的权限衔接。

**B. 绑定三方审批（复用已有集成，中等工作量）**
钉钉/企微已有 `*ApprovalMapping`，飞书有集成文档。模型：创建签署任务时可选发起三方审批，
把外部审批实例 id 写入 `approval_flow_id`，并由三方回调把**审批结论**回写到自建的一张
轻量状态表（仍需一张表存"结论"，否则回调无处落）。豁免条件：租户未绑定三方或未开启审批开关。
风险：审批结论依赖三方回调可达性，需 fail-closed 设计（回调未到 = 未审批）。

**C. 维持透传 + 显式语义标注（零行为变化，本轮建议）**
承认它当前只是**外部单据号留痕**：在实体字段、API 文档与 Swagger 描述里写明
"仅记录外部审批系统单据号，本平台不校验、不构成签署前置条件"，避免后续审计/合规
误以为存在审批控制。等产品定案 A/B 后再升级为控制点。

## 三、若做强制点，应落在哪

- **位置**：`SignFlowService.authorizeTransition` 的 `SUBMIT` 分支（扣配额、建 e签宝流程**之前**）。
  放在 `transition` 里会先扣费再拒绝，产生需对账的脏状态。
- **豁免**：租户级开关（未启用审批即跳过）+ 任务级 `exempt` 标记（如法院/政府通道件）。
- **fail-closed**：启用审批的租户，查不到 APPROVED 结论一律拒绝 SUBMIT；三方回调缺失不得默认通过。
- **配额交互**：审批通过前不扣配额（避免"批不下来但配额已烧"）。

## 四、需要产品回答的问题

1. 审批是**平台内**发生（A）还是**外部系统**发生、平台只记结论（B/C）？
2. 哪些租户/任务类型必须审批？豁免清单是什么？
3. 审批人与签署发起人的关系：租户 owner/admin，还是独立角色？
4. 已发起 e签宝流程后审批被撤回，签署任务应 REVOKE 还是继续？（涉及对 e签宝的撤销调用与配额退还）
5. 审计要求：审批痕迹需保留多久、是否进出证记录？
