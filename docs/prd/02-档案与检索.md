# 档案与检索

档案是公司自有材料（合同、证据、起诉状）。检索的目的是让当前发言槽看到相关原文，而不是把整份文件塞进上下文。

## 上传

- 接口：`POST /api/moot/cases/{id}/files`，multipart
- 单文件上限与现有后端一致：50MB
- 允许的扩展名与签署上传对齐：doc、docx、wps、pdf、xls、xlsx、jpg、jpeg、bmp、png、rtf
- 相对路径：`{tenantId}/{caseId}/files/{文件号}-{文件名}`
- 解析后的路径必须仍在 `jy.archive.dir` 之下，拒绝 `..`
- 原件写入该目录，清单和切片写入同案卷的 `files.json`，并计算 sha256

解析：

- docx 用已有的 poi-ooxml
- 带文字层的 pdf 再引入 PDFBox 或 Tika
- 抽不出字：`parse_status=NO_TEXT`，文件仍可预览，不参与检索
- 解析失败：`FAILED`，保留文件，错误信息落在该行
- 本期不做 OCR

切段：按段落累加，约 500–800 字一段，相邻段重叠约 100 字。写入 `archive_chunk`，带序号。能从解析结果得到页码或段落号才填写定位，不编造页码。

公司级制度文件可以不挂案卷（`case_id` 为空）。本期庭审检索只查挂在当前案卷上的切片。

## 谁来查

点名之前由公司数据平面查。不把「先去调档案接口」写进 Skill 交给模型自觉执行。模型跳过工具调用就会编条款。

查询句由服务端拼：本槽的计划说明，加上一句发言末尾的一段（若已有发言）。模型不决定查不查。

## 怎么查

1. 条件固定为当前租户 + 当前 `case_id`
2. 参数化 `LIKE`，与现有 `KnowledgeService.searchKnowledge` 同一风格
3. 条号、金额、日期按整段去匹配，避免「第 8 条」拆碎后配到别的句子
4. 最多 5 段，每段在消息里最长约 800 字
5. 命中写入 `moot_retrieval`（槽、chunk、实际贴出的摘录）
6. 零命中：消息里写「本槽档案未检索到」

语义上很像、但原文对不上条号的结果，本期丢掉。漏检可以接受，配错条款不能接受。向量检索不在本期。以后若加，索引跟档案文件夹放在一起，不加进平台用户库。

`knowledge_entries` 继续只放平台知识文章。庭审档案不写进那张表。那张表有平台级 `tenant_id IS NULL` 的可见性，和公司正文混在一起会串租户。

## 贴进模型消息的档案部分

只放本槽这 0–5 段，每段前标文件名和 chunk 序号。

这些摘录不写入 `moot_utterance`。下一位收到的庭审记录只有已经说出口的话，不会把原告用过的合同全文和被告用过的合同全文叠在一起。

某一槽若需要核对某一条，靠的是这一次检索贴出的短段。用完不进入笔录全文。

## 预览

`GET /api/moot/cases/{id}/files/{fileId}/content` 在租户和案卷校验通过后按相对路径读盘。一份文件一行，可以打开原件。解析状态在列表里可见：`PENDING`、`PARSED`、`NO_TEXT`、`FAILED`。
