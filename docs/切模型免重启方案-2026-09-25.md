> 状态：代码已按本文落地（2026-09-25）｜ 适用：studio-web + studio-frontend（两仓需同步）
> 选定方案：**A（会话级 `sessions.patch`）** 用于聊天框切模型；**B（`config.patch`）** 用于设置页切默认模型/Provider。
> 协议以本机源码 `D:\Projects\openclaw`（`package.json` version **2026.9.6**，`schemaVersions.state` 18 / `agent` 23）为准，对照文件：`packages/gateway-protocol/src/schema/sessions-patch.ts`、`src/gateway/server-methods/sessions-patch-model-selection.ts`、`src/cli/gateway-cli/run-loop.ts`、`docs/cli/config.md`、`docs/gateway/doctor/config-migrations.md`、`src/commands/doctor/shared/legacy-config-migrations.runtime.entries.ts`。

> 同目录另两份草案（`模型切换热更新方案-2026-09-23.md`、`model-switch-gateway-reload-optimization.md`）只保留根因记录，实施以本文为准。

## 1. 背景与根因

每次在 studio 里切换模型（或切换默认 Provider），都会弹出全局阻塞遮罩并触发 Gateway 重连，体验很差。这是早期 OpenClaw 版本遗留的技术债。

当前链路（以聊天框选模型为例）：

1. `src/pages/Chat/ChatInput.tsx:507` `beginModelSwitch()` → 弹出阻塞遮罩 `ConnectionStatusModal`（`reason === 'model'`）。
2. → `updateAgentModel()` → 服务端 `server/host-core/services/agents-api.ts:70 updateModel`：写 `openclaw.json`，随后调用 `scheduleGatewayReload()`。
3. → `GatewayManager.debouncedReload()` → `reload()`。
4. **关键点**：`server/host-core/gateway/manager.ts:707` —— Windows 不支持 `SIGUSR1` 进程内热重载，直接回退 `restart()`，整个 Gateway 进程 stop + start（约 10–30s），WebSocket 断开重连。

设置页切「默认模型 / Provider」走 `provider-runtime-sync.ts` 的 `syncDefaultProviderToRuntime` → `scheduleGatewayRefresh`，同样是 reload→（Windows）restart。

**结论**：弹窗的本质是「切模型 = 重启 Gateway 进程」。

## 2. OpenClaw 2026.9.6 已支持免重启

9 系列相对 2026.6 是协议和配置形状上的大改。下面只引用 2026.9.6 包内文档，不引用 6.10 的 `gateway/protocol.md` 行号。

- **热加载**：`agents`、`models`、`auth.order`、`auth.profiles`、`broadcast` 等 **不需要重启 Gateway 进程**。默认 `gateway.reload.mode` 是 `hybrid`。`hot` / `restart` 两种旧模式从 `v2026.8.1` 起退役，`openclaw doctor --fix` 会把它们改成 `hybrid`。真正要重启进程的是其余 `gateway.*`（端口、bind、鉴权模式、tailscale、TLS）以及部分 discovery / browser / MCP Apps 监听配置。
- **`sessions.patch`**（`rpc-session-control.md`）：更新会话覆盖，并在响应里返回解析后的 canonical model。会话级字段 `model`、`thinkingLevel`、`fastMode` 需要 `operator.write`；用 `null` 清除覆盖。会话键字段是 **`key`**（与本仓库已有的 `thinkingLevel` 补丁、以及 9.6 的 `sessions.abort` 一致），不是 `sessionKey`。只有管理员发起的模型选择才能顺便写成配置里的 agent 默认；普通 `sessions.patch` 的 `model` 只钉当前会话。用户选中的模型是严格选择：provider/model 不可用时直接失败，不静默走无关 fallback。
- **作用域**：`agents.defaults.modelSelectionScope` 默认是 `"session"`。未显式指定 `-a` / `-g` 时，改模型不改其他聊天，也不改配置默认。选中「当前已生效的默认模型」会清掉会话 pin。`/model default -s` 只清当前会话。
- **`config.patch`**（`config-rpc.md`）：JSON merge patch。已有配置时必须带 `config.get` 返回的 `hash` 作为 `baseHash`。热更新会等到 Gateway 应用这次写入后才返回，响应含 `changedPaths`。控制面写入（`config.apply` / `config.patch` / `update.run`）限流 **每个方法、每个 deviceId+clientIp，30 次 / 60 秒**。6.10 文档里的「3 次 / 60 秒」作废。
- **配置形状**：规范写法是 `agents.entries.<agentId>.model`（字符串 `provider/model`，或 `{ primary, fallbacks }`）。全局默认在 `agents.defaults.model`。`agents.list` 在 9.6 **仍是遗留花名册，不是未知键**：Doctor / 启动迁移会把它收成 `agents.entries` 再删掉 `list`。`openclaw config set|patch|unset` 也接受 `agents.list[0]`，但落盘时写成 keyed roster。一旦文件里已经有 `agents.entries`，再写入的 `agents.list` 会被整段删掉（`legacy-config-migrations.runtime.entries.ts`：entries 已存在则 `delete agents.list`）。Studio 的 `agent-config.ts` 只读 `agents.list`；9.6 迁完之后它会看成空名单，合成一个新的 main，再把 `list` 写回去，模型变更丢失。
- **`sessions.patch` 线格式**（`SessionsPatchParamsSchema`，`additionalProperties: false`）：必填 `key`（非空字符串）。`model` 是可选的 `string | null`。多传 `sessionKey` 会被 schema 拒绝。`thinkingLevel` 同在这张表上，现有思考强度补丁可以原样留着。
- **信号**：9.6 的进程内重启是 **`SIGUSR2`**，由 `commands.restart`（默认 true）放行。`SIGUSR1` 留给 Node 调试器，Gateway **不再监听它**（`run-loop.ts`：never register a listener for SIGUSR1）。Windows 上官方重启走 RPC `gateway.restart.request`，不是对 PID 发 `SIGUSR1`。Studio 的 `GatewayManager.reload()` 在非 Windows 发 `SIGUSR1`、在 Windows 整进程 `restart()`，两条在 9.6 都对不上。
- **还没有会话时**：不要对空 `key` 发 `sessions.patch`。`sessions.create` 可以在创建时带上可选 `model`，与首条消息一起写入。

## 3. 选定方案

把「切模型」从「重启进程」降级为「一次 RPC 调用」，弹窗随之取消。

### 场景 A：聊天框选模型（高频，最烦的那个）—— 会话级 `sessions.patch`

语义：只影响当前会话。与 9.6 默认的 `modelSelectionScope: "session"` 一致。不写 `agents.entries`，不调用 `scheduleGatewayReload`。新开会话仍回到该 agent 原来的默认模型。

实施要点：

1. **沿用已有 Gateway RPC，不必再包一层 `sessionKey`**
   - 仿 `src/stores/chat.ts` 的 `setThinkingLevel`：`hostApi.gateway.rpc('sessions.patch', { key, model })`。
   - `key` 用聊天 store 里的 `currentSessionKey`。`model` 传完整 `provider/model` ref。
   - 选「跟随当前默认」时传 `model: null`，清掉会话 pin。
   - 响应里的 canonical model 用于回显；失败则回滚乐观选中并 toast。
   - 没有 `currentSessionKey` 时先 `sessions.create`（可带 `model`），不要对空 key 发 patch。

2. **前端切模型 handler**（`src/pages/Chat/ChatInput.tsx` `handleSelectModel`）
   - 不再调用 `updateAgentModel`。那条路径会写过时的 `agents.list` 并 `scheduleGatewayReload`。
   - 保留 `setOptimisticModelRef` / `switchingModelRef`（按钮上的转圈）。
   - **移除** `beginModelSwitch` / `endModelSwitch`。

3. **去掉 model 阻塞遮罩**
   - `src/components/common/ConnectionStatusModal.tsx`：删除 `reason === 'model'` 分支（标题/描述）。
   - `src/lib/connection-status.ts:9,21`：`ConnectionReason` 去掉 `'model'`，`deriveConnectionReason` 去掉 `modelSwitchActive` 入参。
   - `src/stores/connection-status.ts`：移除 `modelSwitch` / `beginModelSwitch` / `endModelSwitch`（确认无其它引用，`src/lib/user-session-reset.ts:51` 需同步清理）。
   - 遮罩仅保留真实 Gateway（重）连场景：`connecting` / `reconnecting`。

### 场景 B：设置页切默认模型 / Provider（低频）—— `config.patch`

语义：改配置默认，影响新会话和尚未 pin 的会话。不改其他会话上已有的用户 pin。

实施要点：

1. 网关在线时不要直写文件再 `scheduleGatewayRefresh`。先 `config.get` 取 `hash`，再 `config.patch`：
   - 某个智能体的默认模型：`agents.entries.<agentId>.model` 设为 `"provider/model"`，或 `{ primary, fallbacks }`。
   - 全局默认：`agents.defaults.model.primary`。
   - 只改 model 字段、不删除数组时不要带 `replacePaths`。9.6 的 `replacePaths` 要用精确键（如 `agents.entries.main.skills`），`*` 不能代替子数组授权。
   - 看响应 `changedPaths` 确认落到 `agents.*` / `models.*`。这些路径热加载，进程不重启。
2. **限流**：30 次 / 60 秒 / 方法 / (deviceId+clientIp)。设置页低频即可；短时间内多次默认模型改动做一次 debounce，避免和频道保存叠在同一窗口。
3. 网关离线时可以写文件，但字段必须是 `agents.entries` / `agents.defaults.model`，并且不要再调度 reload。下次启动会读到这份配置。
4. 等待提示用行内 spinner 或非阻塞 toast，不用全屏遮罩。
5. `agents.updateModel` 若仍被「设为该智能体默认」调用：去掉 `scheduleGatewayReload`，写入目标改为 `agents.entries.<id>.model`。聊天框不再走这条 API。

不要采用「删掉 reload、继续直写 `agents.list` 等文件监视」的做法。9.6 迁到 `agents.entries` 之后，后写的 `agents.list` 会被删掉，监视也没有「已应用」回执。`config set`/`config.patch` 接受遗留 `agents.list` 并落成 entries，但 Studio 现在是整文件重写 `list`，不能靠这条兼容。

## 5. 边界与风险

- **会话不存在**：没有 `currentSessionKey` 时先 `sessions.create`（可带 `model`）。不要对空 `key` 发 `sessions.patch`，也不要改用未在 9.6 会话协议里证实的 `chat.send.model`。
- **model ref**：`provider/model` 全称。沿用现有 `modelRef`，不要重复加运行时前缀。`sessions.patch` 会按目标会话所属 agent 的 `modelPolicy.allow` 解析别名；不允许的 ref 会被拒绝。
- **严格失败**：选中的 provider/model 不可用时 Gateway 直接报错。前端 toast，并回滚乐观选中。
- **权限**：会话级 `model` 要 `operator.write`。把选择落成 `agents.entries.*.model` 或 `agents.defaults.model` 要管理员，走场景 B 的 `config.patch`，不要指望普通 `sessions.patch` 顺带改配置。
- **限流**：只有场景 B 的 `config.patch` 受限（30 次/60 秒）。场景 A 不在这份控制面限流里。
- **语义**：聊天框切模型只改当前会话。若产品上要「同时设为该智能体默认」，另走一次场景 B，写 `agents.entries.<id>.model`，仍然不重启。
- **版本差**：先把 `studio-web` / `studio-frontend` 的 `openclaw`（以及本机树里已有的 `@openclaw/discord`、`@openclaw/whatsapp`）从 `2026.6.10` 升到 `2026.9.6`，再改 Studio 写入。进程若仍是 6.10，`agents.entries` 与 `SIGUSR2` 对不上。`@openclaw/qqbot` 与 `@larksuite/openclaw-lark` 不在本机 OpenClaw 树里，升级时单独核对。

## 6. 验证计划

1. 聊天框连续切换多个模型：无全屏遮罩、无 Gateway 重连（观察 `gateway.refresh` 日志不再出现 restart）、回复确实由新模型生成。
2. 切换时 Gateway 进程 PID 不变（`manager.ts` 的 `[gateway-refresh]` 日志应为 hot-apply / 无 restart）。
3. 设置页切默认 Provider：新会话生效，PID 不变，无遮罩。
4. 断网/无效模型：错误如实回显，乐观 ref 回滚。
5. `pnpm run typecheck` + `pnpm run lint:check`（两仓）。
6. Windows 实机验证（restart 回退分支是本次主要痛点来源）。

## 7. 回滚

改动集中在「切模型生效方式」与「遮罩分支」。如出问题，恢复 `ChatInput.handleSelectModel` 调 `updateAgentModel` + `beginModelSwitch`，并恢复 `ConnectionStatusModal` 的 model 分支即可回到旧行为。建议单独成一个 commit 便于回滚。
