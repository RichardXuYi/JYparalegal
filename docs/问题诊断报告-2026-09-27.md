## F0 🔴🔴 公开仓库中的引导凭据可直接登录线上管理员（已实测）

**这是本次核查中严重度最高的一条，且不是理论风险 —— 已成功登录。**

**成因**　三个条件同时成立：

1. 仓库**公开可读**（匿名访问 `github.com/RichardXuYi/JYparalegal` 返回 HTTP 200）；
2. `backend/src/main/resources/application-dev.yml` 中**明文写有引导账号的用户名与口令** —— 第 22–23 行（`ADMIN_BOOTSTRAP_USERNAME` / `ADMIN_BOOTSTRAP_PASSWORD`）、第 28–29 行（`USER_BOOTSTRAP_*`）、第 40–41 行（`COMPANY_BOOTSTRAP_EMPLOYEE*`）。凭据值本身不在本文档中复制，请按行号查阅该文件；
3. 线上服务器正以 `dev` profile 运行并强制启用这些引导账号（见 F1）。

**实测证据**　仅用公开仓库里的信息，经公网域名发起一次管理员登录：

```
POST https://studio.grandpoem.com/api/auth/admin-login
→ {"code":0,"msg":"管理员登录成功",
   "data":{"user":{"id":1,"username":"sssxuyi","role":"ROLE_SUPER_ADMIN",...}}}
→ http 200
```

即：**任何能读该仓库的人（GitHub 公开 = 全网）都已获得线上 `ROLE_SUPER_ADMIN` 入口。**

**暴露窗口**　该文件自 `fe06842`（**2026-09-23 初始提交**）入库，至核查日已公开 **4 天**；该文件在历史中出现于 10 个提交 —— 即使现在改掉，**旧值仍留在 git 历史中可被翻出**。

**是否已被第三方利用**　**未发现迹象**，但样本有限：

- `/var/log/nginx/access.log` 全量 336 条中，登录类 POST 仅 3 条，来源为 `127.0.0.1` 与 `47.116.163.57`，**均为本次核查自身的测试请求**；
- `user_refresh_tokens` 中仅 `xuyi` 有 6 条有效令牌，数量与本次核查的登录测试吻合，无陌生账号会话。
- 局限：日志仅覆盖当前未轮转的文件（约自 9/23 起），且扫描器流量可能已稀释；**不能据此判定绝对未被尝试过**。

**建议方案（按优先级，前两步今天就能做，不需等密钥轮换）**

1. **立即止血（无需改代码）**：DP 已通过 systemd 的 `Environment=` 注入配置，可临时加三行环境变量覆盖 —— `ADMIN_BOOTSTRAP_ENABLED=false`、`USER_BOOTSTRAP_ENABLED=false`、`USER_FULL_ACCESS_ENABLED=false`，然后 `systemctl restart jy-dp`。这样下次启动就不再强制重置口令。

4. **注意 git 历史**：仅改当前文件不足以撤销暴露，旧提交里的值永久可查。若要把仓库维持为公开，需将含明文的提交从历史中抹除（`filter-repo` + 强推）或**直接把仓库改为私有** —— 后者成本最低且立刻见效。无论哪种，都视这三个口令为已泄漏并永久作废。

## F1 🔴 公网服务器以 dev profile 运行

**现象**　`jy-dp.service` 的 `ExecStart` 带 `--spring.profiles.active=dev`，使 `application-dev.yml` 全量生效在一台对外提供公网 API 的机器上。

**证据**　启动日志（`journalctl -u jy-dp`）实测：

```
AdminBootstrapper  - Admin 'sssxuyi' exists; FORCE reset enabled - updating password/email (DEV ONLY)
AdminBootstrapper  - Admin 'sssxuyi' password force-reset (DEV ONLY)
UserBootstrapper   - User 'xuyi' password force-reset (DEV ONLY)
FullAccessBootstrap - 账号 xuyi 已开通全部权限（套餐 PRO）
CompanyDataBootstrapper - 企业数据初始化完成: 公司=grandpoem, 管理员=xuyi, 员工=diandian
```

配套配置（`backend/src/main/resources/application-dev.yml`）：`ADMIN_BOOTSTRAP_FORCE: true`、`USER_BOOTSTRAP_FORCE: true`、`USER_FULL_ACCESS_ENABLED: true`、`COMPANY_BOOTSTRAP_ENABLED: true`、`security.login.max-attempts-per-ip: 100`、`app.cookie.secure: false`。

**影响**

1. 两个账号的口令在**每次启动时被强制改回弱口令**，任何人工改密都会在下次重启后失效；而 `/api/auth/login` 对公网开放。
2. `xuyi` 每次启动被自动授予 PRO，付费校验（`EntitlementInterceptor`）在这台机器上形同虚设。
3. 登录限流放宽至 100 次/IP/15 分钟，为撞库提供条件。
4. `cookie.secure=false` 使会话 cookie 在 HTTP 下不带 Secure 标志。
5. `ProductionConfigValidator` 的 fail-fast 只在 `prod` profile 下生效 —— 上述弱配置**一个都不会被拦住**，这是问题能长期存在的根因。

**建议方案**

1. 新建 `application-prod.yml`：三组 `*_BOOTSTRAP_*_ENABLED: false`、`max-attempts-per-ip: 10`、`cookie.secure: true`。
2. `jy-dp.service` 改为 `Environment=SPRING_PROFILES_ACTIVE=prod`，并配合 F2、F3 一并切换。
3. 先执行 F2 的密钥轮换，再切 prod，避免 prod 校验器因缺密钥直接拒绝启动。
4. 回滚路径：单元文件改回 `dev` + `daemon-reload` + `restart`。

## F2 🔴 JWT 使用可猜测的开发密钥

**现象**　DP 的 access token 为 HS256（对称签名），密钥在 `/etc/systemd/system/jy-dp.service` 中以明文 `Environment=JWT_SECRET=...` 注入，取值为**一句语义可读的开发占位串**（含 `dev`、`change-in-production` 字样，长度 48，非随机）。值已脱敏，此处不复制。

**影响**　HS256 的保密性即认证强度。该密钥一旦外泄（单元文件被备份进公开仓库、日志打印、截图、配置同步等任一途径），任何人可自行签发 `sub=<任意用户>` 的合法 access token，**完全绕过登录、限流与租户校验**，且服务端无法从 token 本身察觉。

**建议方案**

1. 轮换：`openssl rand -base64 48`，经 F3 的 `EnvironmentFile` 注入，不再写入单元文件。
2. 使 `ProductionConfigValidator` 的强度校验真正生效（依赖 F1 切 prod）。
3. **代价需知悉**：换密钥会使全部已签发 token 立即失效，桌面端用户需重新登录一次，建议择低峰执行。
4. 中期：把跨端令牌改为 RS256 + JWKS（CP 侧已是 RS256/JWKS 方案，DP 可直接复用同一模式），避免共享密钥扩散。

## F4 🟠 Flyway 历史与物理表不一致（补脚本即启动失败）

**现象**　三方各自为政：

| | 内容 |
|---|---|
| `flyway_schema_history` | 13 条成功记录，版本 `001 → 130`（实测 `min=001, max=130`） |
| `src/main/resources/db/migration/`（实际参与启动） | 仅 13 个：V001…V110、V130 |
| `db_migration_backup_20260923_234002/` | 31 个，含 V112、V113、V131–V141、V143–V147（**无 V142**） |
| 物理库 | 68 张表，**已包含** V131+ 才创建的 `contract_template`、`evidence_item`、`certificate_record`、tenant 层的 `tenant_quota`、`sign_task`、`sign_doc` 等 |

**影响**　现网 schema 比 Flyway 认知领先约 16 个版本。后果：

- 一旦有人把 V131+ 脚本放回 `src/main/resources/db/migration/`，Flyway 会尝试**重跑建表**，因对象已存在而失败，DP 直接启动不了。
- 全新环境用当前 classpath 部署，只会建到 V130，**得到的 schema 与现网不同** —— 开发与生产结构性背离，且不会被任何报错提示。
- 现网代码里 57 个显式 `@Table` 实体在库中全部存在（实测无缺失），因此**当前运行无恙**；风险在于下一次迁移或新环境部署。

**建议方案（按顺序，不可跳步）**

1. 先冻结：不要往 `resources/db/migration/` 放 V131+ 脚本。
2. 校对差异：对每个备份脚本执行 `SELECT` 确认其对象是否已在库中，形成"已物理存在但历史缺失"的清单。
3. 用 **Flyway `baseline` / 手工补 `flyway_schema_history` 行（`success=1`，checksum 取实际文件值）** 的方式把历史推进到与物理库一致，而非重放 DDL。
4. 补一个 `V900__assert_schema.sql` 式的启动自检（或 CI 里 `mvn flyway:validate` 对临时库跑全新迁移），让"新环境 schema ≠ 现网"这类问题在构建期暴露。
5. `application.yml` 目前 `ignore-pending-migrations: true`、`ignore-missing-migrations: false`、`validate-on-migrate: true` —— 修完历史后建议保持 `validate-on-migrate=true`，它是唯一还能发现此类漂移的机制。

## F5 🟠 真实路径含零宽字符，可重启性依赖软链

**现象**　工作区目录名实际是 `JYparalegal` + **U+200C（零宽非连接符）**，肉眼不可见。9/27 10:37 三个服务从 `/opt/backend`、`/opt/control-plane` 启动，约 10:40 该两目录被改名为此，导致单元文件的 `WorkingDirectory` 与 `ExecStart` jar 路径同时失效。

**证据**

```
$ readlink /proc/<旧DP主进程>/cwd
/opt/JYparalegal‌/backend          # cwd 跟随改名后的真实路径解析
$ ls /opt/backend                  # 单元文件写的路径
No such file or directory
```

`systemctl is-active` 仍报 `active`，`/actuator/health` 正常 —— 因为 JVM 按 inode 持有已打开的 jar。**这是"假活"：进程健康，但一次重启即永久起不来。** 同机 `jy-studio-web.service` 已因此每 10 秒失败一次，journal 累积 **111,094 行**，错误码 `status=200/CHDIR`。

**本次已做的缓解**

```
/opt/backend       -> /opt/JYparalegal‌/backend
/opt/control-plane -> /opt/JYparalegal‌/control-plane
```

不改任何单元文件即恢复可重启性，DP/CP 已在此状态下成功重启并验证。

**残留风险与建议**　软链接是新的依赖点：删掉它、或把仓库挪走，两个服务立刻回到不可重启状态。根治方案是把工作区改成纯 ASCII 路径（如 `/opt/jyparalegal`）并同步更新两个单元文件，需要 IDE 端重新打开目录。另建议在 CI/部署脚本里加一步"`ls -ld <单元文件路径>` + `systemd-analyze verify`"，不要以 `is-active` 作为健康判据。

## F6 🟠 桌面端自动更新 feed 无承载，且无法单侧修复

**现象**　`studio-frontend` 两处把更新源写死：

- `electron/main/updater.ts` → `const OSS_BASE_URL = 'https://47.116.163.57:8082'`，`provider: 'generic'`，feed 为 `.../latest`
- `electron-builder.yml` → `publish: - provider: generic / url: https://47.116.163.57:8082/latest`

**证据**

- 本机 `8082` **无任何监听**；
- `grep -rns '8082' /etc/nginx/ /etc/systemd/system/ /etc/cron.d/` **零命中** → 这台机器上从未部署过该服务（不是掉了，是没有过）；
- 全盘未发现 electron-builder 更新产物（`latest*.yml`、`*.AppImage`、`*.nupkg`、`*Setup*.exe`），也无 `/opt/updates` 等静态目录。

**影响**　桌面端"检查更新"必然失败。由于 `autoUpdater.autoDownload = false`，表现为报错提示而非崩溃。

**关键约束（决定了不能只改服务端）**

1. feed URL **编译进已安装的客户端**，服务端单改无效；修复必须伴随一次重新打包与分发。
2. `https://<裸IP>` 无法取得可信证书（Let's Encrypt 不为 IP 签发），而 electron-updater 走 Node TLS 校验 → 即使补一个自签服务也连不上。代码注释本身也写了这一点。
3. 退回首签 HTTP 会打开更新链 MITM 风险，注释已明令禁止。

**建议方案（择一）**

- **推荐**：改用 `studio.grandpoem.com`（证书现成、nginx 已就绪），在 nginx 加 `location /updates/` 指向静态目录，feed 变 `https://studio.grandpoem.com/updates/latest`。已验证该域名证书有效期至 2026-12-22、`certbot.timer` 正常续期。
- 或改 `provider: github`（`RichardXuYi/JYparalegal` Releases），仓库公开可读，省去自建静态托管。
- 过渡期：在客户端设置里关闭自动更新入口，避免用户反复看到报错。

## F7 🟡 模拟法庭档案目录不存在

**现象**　`jy.archive.dir: ${ARCHIVE_DIR:./data/archive}`，工作目录为 `/opt/backend`，故解析为 `/opt/backend/data/archive` —— 实测不存在。

## F9 🟡 337 个文件"差异"仅为行尾符

**实测**

```
git diff --shortstat origin/main HEAD -- backend
  → 366 files changed, 31979 insertions(+), 34128 deletions(-)

git diff --ignore-cr-at-eol --shortstat origin/main HEAD -- backend
  →  29 files changed,  1295 insertions(+),  3444 deletions(-)
```

抽样：`AuthController.java` 在 main 上 CRLF 行数 `0`、在 houduan 上 `756`（即全部行）；`V130__legal.sql` 去掉 CR 后两边 sha256 **完全相同**。

**影响**

1. 代码评审信噪比崩塌 —— 真实 29 个文件的改动被 366 文件的噪声淹没（本次分析最初即被误导）。
2. `houduan` 分支上的文件是 CRLF（Windows 侧编辑），`main` 是 LF。
3. 关于 Flyway：本项目现网库对 CRLF 版本的 V130 校验通过（启动日志 `Successfully validated 13 migrations`），可佐证 Flyway 校验和按行计算、**对行尾差异不敏感**；但这是旁证而非官方保证，建议在改动行尾策略后专门跑一次 `mvn flyway:validate` 确认（与 F4 一并做）。

**建议**　在仓库根加 `.gitattributes`：

```
* text=auto eol=lf
*.class binary
*.jar binary
*.png binary
*.pdf binary
```

然后一次性 `git add --renormalize .` 提交归一化。注意：这会产生一次全仓 diff，应与功能改动分开提交。
